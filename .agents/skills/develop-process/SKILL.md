# Web BLE Capture の開発手順

`@AGENTS.md` を開き、制約と依頼の範囲を確認する。`@path` はこのリポジトリのルートを基準とする。参照文書は該当する工程で開く。

## 進め方

要求と現在のファイルを根拠に、完了まで進める。判断に影響する不明点だけ確認し、回答を待つ間も独立した作業を進める。仕様と実装に矛盾があれば記録し、既存実装を例外の許可と解釈しない。

以下の全工程を扱う。変更に適用しない項目は理由を記録する。文書だけの変更ではアプリのユニットテストと E2E テストを適用外にできるが、参照・実行例・追加スクリプトは検証する。

| 工程                     | 作業と確認する成果                                                                                                                                          |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 要求分析                 | 変更範囲、受け入れ条件、対象外、必要な検証を作業ログに定める。                                                                                              |
| 調査                     | 現在のコード、`@package.json`、関連仕様を確認する。API や依存更新は公式資料で調べ、根拠と確認日を残す。                                                     |
| 設計                     | アプリの振る舞いを変える場合は `@docs/spec.md` を更新する。文書・開発手順の設計は作業ログに記す。                                                           |
| 設計レビュー             | 受け入れ条件、制約、データの扱い、異常時の動作、テスト計画を照合し、指摘を解消してから実装する。                                                            |
| 開発                     | プロダクト、ユニットテスト、E2E テストを変更範囲に合わせて実装する。再現可能な自動検証を優先し、既存の依存・実行環境を使う。                                |
| Linter / Formatter       | 変更ファイルを整形し、lint と書式検査を実行する。下記のコマンドを使う。                                                                                     |
| ソースレビュー           | 受け入れ条件、異常系、型、テストの不足を確認する。UI・BLE の変更では `@.agents/skills/develop-process/references/frontend-best-practice.md` を開く。        |
| セキュリティレビュー     | `@.agents/skills/develop-process/references/security.md` を開き、パッケージの脆弱性・サプライチェーン攻撃の危険性と、アプリ自体の脆弱性をそれぞれ評価する。 |
| セキュリティアップデート | レビューで必要になったパッケージ更新とアプリ修正を依頼の範囲で実施し、修正内容を再レビューする。範囲外の問題は影響と必要な対応を報告する。                  |
| テスト実行               | 最終ファイルで必要なユニットテスト、E2E、型検査、SSG ビルドを実行する。修正後は影響を受ける検証を再実行する。                                               |

## 検証

リポジトリのルートで、`@package.json` にある実行手段を確認する。

```sh
npm run format -- <変更ファイル>
npm run format -- --check <変更ファイル>
npm run lint
npm test -- --run
```

アプリを変更した場合は SSG ビルドも検証する。出力先の既存ファイルを消去しないよう、新しい一時ディレクトリを `npm run build -- --outDir <出力先>` に指定する。

型検査と E2E は既存の設定を調べて実行する。未導入なら必要な実行手段を設計し、固定技術スタックの範囲で用意する。jsdom だけの検証を実ブラウザの E2E と扱わない。実機の BLE 接続結果は模擬 API の結果と分けて記録する。

スキルを変更する場合は `@.agents/skills/develop-process/references/skill-validation.md` を開く。

## レビューと完了

設計・ソース・セキュリティの各レビューは、対象、根拠、指摘、合否を記録する。指摘を修正して該当レビューを繰り返し、全ラウンドが合格するまで進める。自動検査の成功だけで内容の妥当性を判断しない。

作業ログは `docs/agent-logs/YYYY-MM-DD_HH-MM-SS_作業内容.md` に保存する。要求と設計、変更ファイル、調査根拠、実行コマンド・終了コード・結果、レビュー結果、適用外の理由、残課題、規則の例外を記録する。例外の記録は許可の代わりにならない。

未解決の対象内の指摘や、実行できない必須検証があれば完了にしない。完了時は変更内容、検証結果、残る制約を簡潔に伝える。
